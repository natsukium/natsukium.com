## 1. ターミナルエミュレータの境界をどこに引くか

最近、コーディングエージェントを並べて管理する専用の GUI アプリや、セッション管理・画面分割・スクリプト拡張を詰め込んだ新しいターミナルエミュレータが次々に登場し、「何が新しくできるか」という機能の数で語られている。一方、ターミナルエミュレータ自身を小さく保とうとする側は、従来どおりそれらの機能を外部のマルチプレクサに委ねてきた。

しかし、多機能化へ進む側でも最小構成を守る側でも曖昧なままになっていたのは、「ターミナルエミュレータ自身がどこまでの仕事を引き受け、どこから先を外部のツールに委ねるか」という責務の境界である。とりわけ「複数のセッションをウィンドウの寿命と切り離して維持すること」と「画面を分割して配置すること」は、それぞれターミナルエミュレータ自身の仕事なのか、それとも外部ツールの仕事なのか。

[felis](https://github.com/felis-terminal/felis) は、この問いに対して「何を引き受け、何をしないか」の線引きをゼロから引き直して設計したターミナルエミュレータである。従来の構成が抱えていた二重構造を解きほぐし、描画・レイアウト・状態維持の役割を分け直した結果、ウィンドウを閉じても生き続けるセッションや、エージェントを含む外部プログラムからの制御がそのまま手に入る構造になった。

## 2. 二重構造の代償と「文字だけでいい」という前提

従来の構成における二重構造の典型が、ターミナルエミュレータの上でセッション維持や画面分割のために `tmux` を動かす構成である。タブや分割を持たない Alacritty のようなターミナルだけでなく、それらの機能を備えたターミナルの上でも `tmux` を併用している利用者は多い。この構成では、外側のターミナルエミュレータの内側に、`tmux` というもう一つ別のターミナルエミュレータを挟み込むことになる。

内側に別のエミュレータを挟むことには、速度と表現力の2つの代償が伴う。まず、シェルの出力が2つのエミュレータを通るため、速さを求めて高速なターミナルを選んでおきながら前段の `tmux` で速度を落としてしまう。さらに、アプリケーションが使える表現力も「外側のターミナルと内側の `tmux` の双方が解釈でき、かつ `tmux` がパススルーできるもの（積集合）」に制限されるため、Kitty Graphics ProtocolやText Sizing Protocol、Kitty Keyboard Protorolが削られ、スクロールバックも二重管理になる。

この代償を受け入れる理由として、「ターミナルは文字さえ出ればいい」という主張がよく聞かれる。しかし、ターミナルが扱う「文字」の範囲は、ASCII からマルチバイト文字、絵文字、Nerd Fonts へと広がり続けてきた。「文字だけ」とは現在の自分が使っている範囲を文字と呼んでいるにすぎず、今日の画像表示やテキストサイズ変更のプロトコルを「文字ではない」と切り捨てる根拠は、過去の線引きと同じく暫定的である。

一度「ターミナルの描画」を責務として引き受けたなら、ミニマリズムを理由に描画の忠実度や速度を省くわけにはいかない。「小さくスクリプトを持たないターミナルであること」と「プロトコル対応を絞ること」は別の決定であり、切り離せる。felis は、引き受けた描画の責務の中では妥協せず、責務の外には出ないという基準を採る。同じ入力に対して Kitty が正確に表示できるなら、表示できないのは felis の機能不足ではなくバグである。

## 3. レイアウトとワークフローを外部へ委ねる

引き受ける「描画」の基準を定めたうえで、次はこれまで `tmux` が担っていた仕事をどう切り分けるかが問題になる。そもそも `tmux` がターミナルの内側にもう一つエミュレータを抱える二重構造になっていたのは、本来独立した2つの仕事である「画面の分割・配置（レイアウト管理）」と「プロセスの寿命管理（セッションの維持）」を一つのプロセスでまとめて担っていたからである。この2つを切り離し、レイアウトやワークフローの拡張を外部へ委ねるうえで手本にしたのが、テキストエディタである [Kakoune の設計](https://github.com/mawww/kakoune/blob/master/doc/design.asciidoc)だ。Kakoune がウィンドウ分割や巨大なスクリプト言語ランタイムを内部に抱え込むのをやめ、配置をウィンドウマネージャ（WM）に、拡張を外部プログラムに委ねたのと同じ分割をターミナルエミュレータに適用する。

もちろん、タブやペインをターミナルから外すことに対しては、「`tmux` や内蔵ペインならどの OS でも同じキーバインドで操作を持ち運べる」という反論があるだろう。確かに OS をまたいでターミナル固有のペイン操作を揃える点では `tmux` に分があるが、その代価として常に Prefix キーを押してから操作する2段階の入力になり、OS 標準のショートカットとも切り離される。しかも、ターミナルがペインを持たなくても描画の忠実度は損なわれない。そのため felis は「1ウィンドウ＝1シェル」に徹してレイアウトを WM に任せ、各環境のブラウザやエディタとキー操作を揃える道を選んだ（SSH 先での操作をどう揃えるかは4節の末尾で述べる）。

同じ線引きから、felis はタブ・分割・ペインを持たないだけでなく、`tmux` パススルーにも対応しない。設定や操作のための埋め込みスクリプト言語も持たず、ワークフローの拡張はバージョン管理された公開 IPC を通じてシェルと外部プログラム（`fzf` や `jq` など）で行う。

## 4. 画面の再生か、状態の転送か

レイアウトを WM に委ねたなら、もう一つの仕事である「セッションの維持」も、レイアウト機能を省いて永続化だけに特化した外部ツールに任せればよいように思えるかもしれない。しかし、外側に別のターミナルがある限り、再接続時には内部で保持している画面状態をエスケープシーケンスとして手元のターミナルへ送り直し、画面を描き直させる方式にならざるを得ない。初期のセッション維持ツールである `dtach` や `abduco` はそもそも画面の状態を持たず、内部にターミナルエミュレーションのライブラリを組み込んで状態を保持する [`zmx`](https://erock.prose.sh/zmx-session-persistence) も、再接続時には `tmux` と同様、その状態をエスケープシーケンスとして手元のターミナルへ送り直して画面を作り直す。

このような「画面の再生」方式では、送り側と受け側の2つのエミュレータが同じ解釈をすることに画面の復元が依存してしまう。実際、`zmx` でも再接続時にキーボードプロトコルの設定を送り直すため一部のプログラムがそのシーケンスを画面にそのまま表示してしまったり、SSH 越しに入れ子にするとカーソル位置が壊れたりする問題が[挙げられている](https://erock-git-zmx.pgs.sh/tree/main/item/README.md.html)。

したがって、2つのエミュレータ間の解釈のずれをなくすには、ターミナル自身がセッション維持の仕組みを持つ必要がある。ただし、[WezTerm のマルチプレクサ機能](https://wezterm.org/multiplexing.html)のように、単一プロセスでの動作が既定であり、サーバー分離が明示的に有効化するオプションにとどまる設計では、その経路特有の[性能](https://github.com/wezterm/wezterm/issues/7527)や[メモリ](https://github.com/wezterm/wezterm/issues/8298)、[状態同期](https://github.com/wezterm/wezterm/issues/1237)の問題が残りやすい。

このため felis には単一プロセスで完結するモードがなく、すべてのウィンドウは最初から **daemon** の **client** として動く。セッションの生の状態（PTY、グリッド、スクロールバック、画像というメカニズム）は daemon が保持し、ピクセルへの描画（フォント、色、シェーピングという見た目のポリシー）は client が担う。外部ツールの方式が「画面の状態をエスケープシーケンスとして送り直す『画面の再生』」であるのに対し、felis の方式は「daemon が保持する構造化された状態をそのまま渡す『状態の転送』」である。クライアントを閉じてもシェルとスクロールバックは常に daemon 上に残り、再接続時には転送された状態を client が直接描画する。転送プロトコルと描画器の実装が確かであることは引き続き必要だが、2つのエミュレータ間の解釈のずれは原理的になくなる。

この daemon と client の分離によって、3節で残していた「SSH 先でも同じ操作をしたい」という要求もそのまま解決する。リモート側に `tmux` の操作体系を持ち込むのではなく、手元の client からリモートの daemon に直接つなぐことで応えるからである。ローカルの永続化もリモート接続も同じ状態転送の仕組みの上で動くため、手元の WM の操作感のままリモートのセッションをローカルと同じウィンドウとして扱える。

## 5. コードの共有か、状態の共有か

4節で挙げた `zmx` が内部で状態保持に使っているのが、Ghostty から切り出されたターミナルエミュレーションのライブラリ [`libghostty`（`libghostty-vt`）](https://lib.ghostty.org/)である。エージェント向けの専用ターミナルである [`cmux`](https://cmux.com/) や IDE、Emacs の [`ghostel`](https://dakra.github.io/ghostel/) といったエディタの組み込みターミナルにこのライブラリを採用する動きは[広がっており](https://github.com/Uzaaft/awesome-libghostty)、先日 v1.0 として安定 C ABI が提供されたことでさらに定着しつつある。

しかし、`libghostty` が提供するのは「エミュレーションの実装を各プロセスに組み込む『コードの共有』」であり、プロセスをまたいで同じセッションを扱う仕組みではない。IDE、エディタ、専用ターミナルがそれぞれ同じライブラリを組み込んでも、各自のプロセス内部に閉じたシェルが乱立するだけで、あるアプリで起動したセッションを別のアプリから引き継ぐことはできない。象徴的なのは、Ghostty の作者自身が設立した Superlogical で、セッションの永続化やリモート接続を扱うために [`Rex`](https://www.bitdoze.com/superlogical-rex/) という別のターミナルアプリケーションを新たに作っていることだ。エミュレーションのコードをライブラリとして切り出す設計だけでは、セッションの維持や共有という問題が解決しないことを、この別アプリの登場自体が示している。

それでは、セッション共有の仕組み（daemon）だけを作り、その内部の VT（仮想端末）エンジンには `libghostty` を組み込めばよいのではないか。felis がその構成を採らない一つ目の理由は、レイアウトやスクリプトを外部へ委ねた felis にとって、制御シーケンスを解釈して画面の状態を構築し描画へ渡す部分こそが、ターミナルエミュレータとして引き受ける中核の責務だからである。その中核を既存ライブラリに委ねて薄いラッパーを作るのではターミナルエミュレータを新しく作る意味がないし、4節で述べた「構造化された状態の転送」や2節の「描画の忠実度」に最後まで責任を持つには、状態の表現から自前で設計する必要がある。

二つ目の理由は、単一のライブラリに実装が収束することの危うさにある。あらゆるツールが同じライブラリに依存すれば、事実上の仕様が「`libghostty` がどう解釈するか」に収束し、バグや解釈の癖も採用ツール全体へ一斉に広がる。felis は、Kitty の画像・キーボードプロトコルのようなワイヤー上の仕様は共有しつつ、それを解釈する VT エンジン自体は独立して実装する立場をとる。複数の独立した実装が同じプロトコルを解釈することで初めて、仕様の曖昧な点が見えるようになる。

この自前の VT エンジンを持つ単一の daemon を中心に据えることで、felis は「プロセスから独立した単一のセッション群を複数のクライアントで扱う『**状態の共有**』」を行う。GUI クライアントや CLI、さらには実験段階にある TUI・Web・Emacs の各クライアントは、すべて1つの daemon が保持する同じセッション群を別の形で表示・操作しているだけである。

## 6. コーディングエージェントからのヘッドレス制御

felis はコーディングエージェントのために作ったターミナルエミュレータではない。しかし、5節で述べた「単一の daemon が状態を保持し、GUI や CLI などの複数のクライアントが同じセッション群を操作する」構造からは、ウィンドウより長く動き続けるエージェントを扱うのに必要な仕組みがそのまま出てくる。すべてのセッションは最初からウィンドウと独立して daemon 上で動くため、エージェントは CLI クライアントを通じて、ウィンドウを一切開かずにセッションの作成、キー入力の送信、コマンド完了の待機、画面や出力の読み取りができる。人間が介入したいときだけ、後からそのセッションに GUI のウィンドウをアタッチすればよい。

この線引きがエージェントの要求と重なることは、エージェント向けのツールである [`herdr`](https://herdr.dev/core/) の変遷からも見て取れる。`herdr` はもともとエージェントを扱うための `tmux` 風の TUI として登場したが、現在では画面を持たないヘッドレスなデーモン（[`herdr-core`](https://github.com/herdrdev/herdr-core)）を分離し、CLI からの操作と TUI・GUI（`herdr-app`）の各クライアントをその上に載せる構成へと辿り着いている。「ターミナルエミュレータの境界」から出発した felis と、「エージェント向けの TUI」から出発したツールが、逆の方向から同じデーモン分離に行き着いたことになる。

## 7. 動作環境と導入方法

felis は、ウィンドウ管理やワークフローをすでに自分の道具で組んでおり、ターミナルエミュレータにもその一員として振る舞ってほしい人に向けたツールである。現在は `0.x` の初期リリースで、`x86_64-linux`、`aarch64-darwin`、`x86_64-pc-windows-msvc` をサポートしている。Nix 環境であれば `nix run github:felis-terminal/felis` で今すぐ試すことができる。その他の環境での導入手順や、ベンチマーク、設計ドキュメントは [GitHub リポジトリ](https://github.com/felis-terminal/felis)を参照してほしい。

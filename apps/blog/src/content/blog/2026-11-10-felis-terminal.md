## 1. ターミナルエミュレータの境界をどこに引くか

近年、セッション管理・画面分割・スクリプト拡張を備えた新しいターミナルエミュレータが次々に登場し、機能の多寡で比較される場面が増えた。一方、ターミナルエミュレータ自身を小さく保とうとする側は、従来どおりそれらの機能を外部のマルチプレクサに委ねてきた。

しかし、多機能化へ進む側でも最小構成を守る側でも問い直されないままだったのは、「ターミナルエミュレータ自身がどこまでの仕事を引き受け、どこから先を外部のプログラムに委ねるか」という責務の線引きである。とりわけ「複数のセッションをウィンドウの寿命と切り離して維持すること」と「画面を分割して配置すること」は、それぞれターミナルエミュレータ自身の仕事なのか、それとも外部プログラムの仕事なのか。

[felis](https://github.com/felis-terminal/felis) は、この問いに対して「何を引き受け、何をしないか」の境界を引き直して設計したターミナルエミュレータである。入出力と描画に加えてセッション維持は本体側で引き受け、レイアウトとワークフロー拡張を外部へ委ねる役割分担を採った結果、ウィンドウを閉じても維持されるセッションと、外部プログラムからの制御を実現する構造になった。

## 2. 二重構造の代償と「文字だけでいい」という前提

従来の構成では、セッション維持や画面分割のためにターミナルエミュレータの中で `tmux` を動かす構成が一般的である。タブや分割を持たない Alacritty のようなターミナルだけでなく、それらの機能を備えたターミナルでもセッション維持などのために `tmux` を併用している利用者は多い。`tmux` 自身もエスケープシーケンスを解釈して仮想画面を保持するため、結果として外側のターミナルエミュレータの内側に、もう一つ別のターミナルエミュレータを挟み込む二重構造になる。

内側に別のエミュレータを挟むことには、3つの代償が伴う。

一つ目は速度である。シェルの出力が2つのエミュレータを通るため、高速なターミナルを選んでも内側の `tmux` での再解釈がボトルネックとなり全体の速度が落ちる。

二つ目は表現力である。アプリケーションが使える機能が「外側のターミナルと内側の `tmux` の双方が解釈でき、かつ `tmux` がパススルーできるもの（積集合）」に制限されるため、Kitty Graphics Protocol や Text Sizing Protocol、Kitty Keyboard Protocol のような新しいプロトコルは、`tmux` 側でパススルーの設定が必要になったり、そもそも未対応だったりして制約を受け、そのままでは使えないことが多い。

三つ目は状態の重複と操作の食い違いである。スクロールバックを外側と内側で二重に管理するためメモリ消費が増えるうえ、内側が独自の画面やペインを保持することで、外側の検索や履歴操作が内側の表示と噛み合わなくなる。

このうち表現力の制約を問題視しない理由として、「ターミナルは文字さえ出ればいい」という主張がよく聞かれる。しかし、ターミナルが扱う「文字」の範囲は、ASCII からマルチバイト文字、絵文字、Nerd Fonts へと広がり続けてきた。「文字だけ」という言い分は、現在使われている範囲を文字と呼んでいるにすぎず、今日の画像表示やテキストサイズ変更のプロトコルを「文字ではない」と切り捨てる根拠は、過去の線引きと同じく暫定的である。

「小さくスクリプトを持たないターミナルであること」と「プロトコル対応を絞ること」は別の決定であり、切り離せる。したがって、一度「ターミナルの入出力と描画」を責務として引き受けたなら、ミニマリズムを理由に忠実度や速度を妥協する必要はない。felis は、引き受けた入出力と描画の責務の中では妥協せず、責務の外には出ないという基準を採る。先述した画像やテキストサイズ、キーボードの拡張を含む主要プロトコルについて、実装で先行する Kitty が同じ入出力を正確に処理できるなら、felis で処理できないのは機能不足ではなくバグとして扱う。

## 3. レイアウトとワークフローの分離

引き受ける「入出力と描画」の基準を定めたうえで、次は画面の分割・配置（レイアウト管理）と、作業手順の自動化や外部プログラムとの連携（ワークフロー拡張）をどう切り分けるかが問題になる。この切り分けで手本にしたのが、テキストエディタ [Kakoune の設計](https://github.com/mawww/kakoune/blob/master/doc/design.asciidoc)である。Kakoune はウィンドウ分割や巨大なスクリプト言語ランタイムを内部に抱え込むのをやめ、配置をウィンドウマネージャ（WM）に、ワークフローの拡張を外部プログラムに委ねている。

もちろん、タブやペインをターミナルから外して WM に任せることに対しては、「`tmux` や内蔵ペインならどの OS でも同じキーバインドを使い回せる」という反論があるだろう。確かに OS をまたいでターミナル固有のペイン操作を揃える点ではそれらの方式に分があるが、その代償として `tmux` では常に Prefix キーを押す2段階の入力になり、内蔵ペインでも OS ごとの作法やブラウザ・エディタなどのショートカットとは別の操作体系になる。そのため felis は Kakoune と同じ切り分けを採り、「1ウィンドウ＝1シェル」に徹してレイアウトを WM に任せ、各環境のブラウザやエディタとキー操作を揃える設計にした（SSH 先での操作をどう揃えるかは4節の末尾で述べる）。

同じ線引きから、felis はタブ・分割・ペインを持たず、設定や操作のための埋め込みスクリプト言語も持たない。ワークフローの拡張は、セッションやウィンドウを外部から操作するためのバージョン管理された公開 IPC を通じて、シェルや外部プログラム（`fzf` や `jq` など）との連携で行う。なお、`tmux` を内側に挟む二重構造を前提としないため、`tmux` パススルーにも対応しない。

## 4. 画面の再生か、状態の転送か

レイアウトを WM に委ねたなら、`tmux` が担っていたもう一つの仕事である「セッションの維持」（プロセスの寿命管理）も、レイアウト機能を省いて永続化だけに特化した外部プログラムに任せればよいように思えるかもしれない。しかし、外側に別のターミナルがある限り、再接続時には内部で保持している画面状態をエスケープシーケンスとして手元のターミナルへ送り直し、画面を描き直させる方式にならざるを得ない。初期のセッション維持プログラムである `dtach` や `abduco` はそもそも画面の状態を持たないため再接続時に直前の表示を復元できず、内部にターミナルエミュレーションのライブラリを組み込んで状態を保持する [`zmx`](https://erock.prose.sh/zmx-session-persistence) も、再接続時には `tmux` と同様、その状態をエスケープシーケンスとして手元のターミナルへ送り直して画面を作り直す。

このような「画面の再生」方式では、送り側と受け側の2つのエミュレータが同じ解釈をすることが画面復元の前提になる。実際、[`zmx` の README](https://erock-git-zmx.pgs.sh/tree/main/item/README.md.html) でも、再接続時にキーボードプロトコルの設定を送り直すため一部のプログラムがそのシーケンスを画面にそのまま表示してしまったり、SSH 越しに入れ子にするとカーソル位置が壊れたりする問題が挙げられている。したがって、2つのエミュレータ間の解釈のずれをなくすには、ターミナル自身がセッション維持の仕組みを持つ必要がある。

しかし、ターミナル自身がセッション維持の機能を持っていても、[WezTerm のマルチプレクサ機能](https://wezterm.org/multiplexing.html)のように、単一プロセスでの動作が既定であり、サーバー分離が明示的に有効化するオプションにとどまる設計では、開発や利用の中心が既定の単一プロセス構成に偏り、別経路である分離構成の最適化や状態管理の整合性が後回しになりやすい。その結果、サーバー分離を有効にした構成特有の[性能](https://github.com/wezterm/wezterm/issues/7527)や[メモリ](https://github.com/wezterm/wezterm/issues/8298)、[状態同期](https://github.com/wezterm/wezterm/issues/1237)の問題が残り続ける。

このため felis には単一プロセスで完結するモードがなく、すべてのウィンドウは最初からデーモンのクライアントとして動く。セッションの状態（PTY、グリッド、スクロールバック、画像）はデーモンが保持し、ピクセルへの描画（フォント、色、シェーピング）はクライアントが担う。

このように、外部プログラムの方式が画面の状態をエスケープシーケンスとして送り直す「画面の再生」であるのに対し、felis の方式はデーモンが保持する構造化された状態をそのまま渡す「状態の転送」である。クライアントを閉じてもセッションはデーモン上に残り、再接続時には転送された状態をクライアントが直接描画する。転送プロトコルと描画器の実装が確かであることは引き続き必要だが、クライアント側にはエスケープシーケンスを再解釈する層がないため、2つのエミュレータ間の解釈のずれは原理的になくなる。

このデーモンとクライアントの分離によって、3節で残していた「SSH 先でも同じ操作をしたい」という要求もそのまま満たせる。リモート側に `tmux` の操作体系を持ち込むのではなく、手元のクライアントからリモートのデーモンに直接つなぐからである。ローカルの永続化もリモート接続も同じ状態転送の仕組みの上で動くため、ウィンドウ管理やキー操作については、手元の WM の操作感のまま、リモートのセッションをローカルと同様に扱える。

## 5. コードの共有か、状態の共有か

4節で挙げた `zmx` が内部で状態保持に使っているのが、Ghostty から切り出された仮想端末エンジン（以下 VT エンジン）のライブラリ [`libghostty`（`libghostty-vt`）](https://lib.ghostty.org/)である。エージェント向けの専用ターミナルである [`cmux`](https://cmux.com/)、IDE、あるいは Emacs の [`ghostel`](https://dakra.github.io/ghostel/) といったエディタの組み込みターミナルにこのライブラリを採用する動きは、v1.0 で安定 C ABI が提供されたこともあり[広がっている](https://github.com/Uzaaft/awesome-libghostty)。

しかし、`libghostty` が実現するのはエミュレーションの実装を各プロセスに組み込む「コードの共有」であり、プロセスをまたいで同じセッションを扱う仕組みではない。IDE、エディタ、専用ターミナルがそれぞれ同じライブラリを組み込んでも、各自のプロセス内部に閉じたシェルが乱立するだけで、あるアプリで起動したセッションを別のアプリから引き継ぐことはできない。実際、Ghostty の作者自身が設立した Superlogical でも、セッションの永続化やリモート接続を扱うために [`Rex`](https://www.bitdoze.com/superlogical-rex/) という別のターミナルアプリケーションを新たに作っている。

それでは、セッション共有の仕組み（デーモン）だけを作り、その内部の VT エンジンには `libghostty` を組み込めばよいのではないか。felis がその構成を採らない理由は2つある。

一つ目の理由は、レイアウトやスクリプトを外部へ委ねた felis にとって、エスケープシーケンスを解釈して画面の状態を構築し描画へ渡す部分こそが、ターミナルエミュレータとして引き受ける中核の責務だからである。その中核を既存ライブラリに委ねてしまえば、上流のデータ構造や API の制約に縛られ、4節で述べた「構造化された状態の転送」や2節の「入出力と描画の忠実度」に必要な拡張や修正を自前の判断だけで完結できない。フォークして独自に維持し続けるなら、外部ライブラリを使う利点も薄れる。したがって、状態の表現から自前で設計する必要がある。

二つ目の理由は、単一のライブラリに実装が収束することの危うさにある。多くのターミナルやエディタが単一のライブラリに依存すれば、事実上の仕様が「`libghostty` がどう解釈するか」に収束し、バグや解釈の癖も採用アプリケーション全体へ一斉に広がる。felis は、Kitty の画像・キーボードプロトコルのような通信プロトコルの仕様は共有しつつ、それを解釈する VT エンジン自体は独立して実装する立場をとる。複数の独立した実装が同じプロトコルを解釈することで初めて、仕様の曖昧な点が見えるようになり、特定の実装の癖が事実上の標準になるのを防げる。

この自前の VT エンジンを持つ単一のデーモンを中心に据えることで、felis が実現するのはプロセスから独立した単一のセッション群を複数のクライアントで扱う「状態の共有」である。GUI クライアントや CLI、さらには実験段階にある TUI・Web・Emacs の各クライアントは、すべて1つのデーモンが保持する同じセッション群をそれぞれの形で表示・操作しているだけである。

## 6. コーディングエージェントからのヘッドレス制御

felis はコーディングエージェントのために作ったターミナルエミュレータではない。しかし、5節で述べた「単一のデーモンが状態を保持し、GUI や CLI などの複数のクライアントが同じセッション群を操作する」構造は、ウィンドウを閉じた後もエージェントがヘッドレスで動き続け、後から人間が介入できるようにするという要件を追加の仕組みなしに満たす。すべてのセッションは最初からウィンドウと独立してデーモン上で動くため、エージェントは CLI クライアントを通じて、ウィンドウを一切開かずにセッションの作成、キー入力の送信、コマンド完了の待機、画面や出力の読み取りができる。人間が介入したいときだけ、後からそのセッションに GUI のウィンドウをつなげばよい。

この線引きがエージェントの要求と重なることは、エージェント向けのセッション管理 TUI である [`herdr`](https://herdr.dev/core/) の変遷からも見て取れる。`herdr` はもともとエージェントを扱うための `tmux` 風の TUI として登場したが、現在では画面を持たないデーモン（[`herdr-core`](https://github.com/herdrdev/herdr-core)）を分離し、CLI からの操作と TUI・GUI の各クライアントをその上に載せる構成へと移行している。「ターミナルエミュレータの境界」から出発した felis と、「エージェント向けの TUI」から出発した `herdr` が、異なる出発点から同じデーモン分離の設計に収束したことになる。

## 7. 対象読者と導入方法

felis は、ウィンドウ管理やワークフローをすでに自分の道具で整えており、ターミナルエミュレータもその一部として組み込みたい人に向けたソフトウェアである。

試用したい場合は、`0.x` の初期リリースを利用できる。対応環境は `x86_64-linux`、`aarch64-darwin`、`x86_64-pc-windows-msvc` で、Nix 環境であれば `nix run github:felis-terminal/felis` で起動できる。その他の環境での導入手順や、ベンチマーク、設計ドキュメントは [GitHub リポジトリ](https://github.com/felis-terminal/felis)を参照してほしい。
